### 1. Объект ревьюирования
**Объект:** Функция `final_total`, реализующая расчёт итоговой стоимости заказа с учётом доставки и промокода.
**Почему требует проверки:** Функция затрагивает денежную логику системы (расчёт скидок и стоимости доставки). Ранее в ней была выявлена регрессия при переходе на новую версию (потеря бесплатной доставки на границе 3000 ₽), поэтому изменения в этом модуле критичны для бизнеса.

### 2. Цель ревьюирования
Цель проверки — убедиться, что новая версия функции корректно обрабатывает скидки и граничные значения, не нарушает работу других частей системы (не содержит регрессий), соответствует бизнес-требованиям и написана понятным, поддерживаемым кодом.

### 3. Участники процесса
- **Автор изменений:** Разработчик, написавший новую версию функции.
- **Ревьюер:** Другой разработчик или старший специалист, который проверяет логику кода и ищет потенциальные проблемы.
- **Тестировщик (QA):** Проверяет поведение функции на реальных сценариях и подтверждает исправление ошибок.
- **Ответственный за слияние (Release Manager / Team Lead):** Проверяет прохождение всех автоматических проверок и принимает финальное решение о слиянии в основную ветку.

### 4. План этапов ревьюирования

| Этап | Ответственный | Действия | Результат |
|---|---|---|---|
| **Подготовка** | Автор | Делает локальные коммиты, запускает автотесты, проверяет отсутствие лишнего кода | Ветка с изменениями готова, отправлена в удалённый репозиторий |
| **Создание MR** | Автор | Открывает Merge Request (или Pull Request), описывает суть изменений | Ссылка на MR доступна команде |
| **Предварительные проверки** | CI/CD (автомат) | Запуск линтера, статического анализатора, автотестов на сервере | Все автоматические тесты пройдены (зелёный статус) |
| **Изучение кода** | Ревьюер | Читает код, сверяет с бизнес-требованиями, проверяет граничные случаи | Замечания (если есть) или одобрение (Approve) |
| **Фиксация замечаний** | Ревьюер | Оставляет комментарии в MR к конкретным строкам кода | Замечания оформлены |
| **Исправление** | Автор | Вносит правки в код, делает новые коммиты в ту же ветку | Обновлённая версия кода в ветке |
| **Повторная проверка** | Ревьюер и CI/CD | Перепроверяет исправленные места, ждёт повторного прохождения тестов | Замечания закрыты, тесты пройдены |
| **Принятие решения** | Team Lead | Проверяет, что все замечания сняты и требования выполнены | Изменения влиты в основную ветку (Merge) |

### 5. Критерии проверки

| № | Критерий | Как проверить |
|---|---|---|
| 1 | Соответствие требованиям | Проверить, что скидка вычитается до сравнения с порогом, а самовывоз работает без доставки |
| 2 | Обработка граничных значений | Проверить работу при сумме ровно 3000 ₽ (с учётом скидки и без) |
| 3 | Обработка недопустимых данных | Проверить, что при отрицательной скидке сумма не увеличивается |
| 4 | Наличие тестов | Убедиться, что для новой логики написаны юнит-тесты (особенно на граничные случаи) |
| 5 | Отсутствие регрессий | Убедиться, что старые вызовы функции адаптированы под новую сигнатуру и работают корректно |
| 6 | Качество кода | Проверить, что код читаем, переменные названы логично, нет дублирования условий |

### 6. Инструментальные средства
- **IDE (редактор кода):** Visual Studio Code (с расширениями для Python) — для написания кода и локальной проверки.
- **Система контроля версий:** Git и **GitHub** — для хранения кода, создания ветки и Merge Request.
- **Статический анализ:** `flake8` или `pylint` (встроены в CI GitHub Actions) — проверяют синтаксис и стиль кода.
- **Автотесты:** `pytest` — запускается автоматически при пуше изменений.
- **Фиксация комментариев:** Встроенный интерфейс Pull Request на GitHub — позволяет оставлять комментарии к конкретным строкам кода (Diff).

### 7. Фиксация замечаний
Все замечания оставляются в виде комментариев в Pull Request на GitHub. Ревьюер привязывает комментарий к конкретной строке кода (через режим *Files changed*). Автор получает уведомление на почту. Вопрос считается рассмотренным, когда автор отвечает на комментарий (что он сделал) и нажимает кнопку **Resolve conversation**.

**Пример корректно сформулированного комментария:**
> `suggestion:` В строке 15 используется строгое неравенство `total > 3000`. По требованиям при сумме ровно 3000 ₽ доставка должна быть бесплатной. Рекомендую заменить на `total >= 3000`.

### 8. Исправление выявленных проблем
Автор читает замечания в PR, вносит изменения в код в своей локальной ветке, делает новый коммит с понятным сообщением (например, `Fix: изменил > на >= согласно замечанию`) и отправляет изменения на сервер (`git push`). В PR-интерфейсе автор отвечает на комментарий ревьюера и нажимает **Resolve conversation**, подтверждая, что работа выполнена.

### 9. Повторное ревьюирование
После внесения исправлений ревьюер:
1. Проверяет только новые коммиты (вкладка *Commits* в PR).
2. Убеждается, что исходная проблема устранена (например, условие заменено на `>=`).
3. Смотрит, не появились ли новые ошибки в соседних строках.
4. Проверяет статус CI/CD — все обязательные автотесты и линтеры должны быть «зелёными».

### 10. Правила доступа к репозиторию
- **Ветка `main` (основная) защищена:** прямой пуш (git push) в неё запрещён.
- **Автор:** имеет права создавать ветки (например, `feature/final-total-update`) и открывать Pull Requests.
- **Ревьюеры:** имеют права оставлять комментарии и одобрять (Approve) изменения.
- **Team Lead:** имеет права на слияние (Merge) одобренных PR в ветку `main`.
- **Запрет:** Ни при каких условиях в код не попадают пароли, токены и секретные ключи. Все секреты хранятся в переменных окружения (GitHub Secrets).

### 11. Итоговое решение
Изменения могут быть приняты (влиты в основную ветку), если:
1. Все существенные замечания ревьюера устранены (статус Resolve).
2. Автоматические проверки (линтеры, тесты) пройдены успешно.
3. PR имеет необходимое количество одобрений (минимум 1 Approve от ревьюера).
4. Ветка не имеет конфликтов слияния (Merge conflicts) с основной веткой.

**Вывод:** Предложенный план позволяет контролировать качество на всех этапах. Ревьюирование не сводится только к визуальному чтению кода. Автоматические проверки (тесты и линтеры) отсеивают базовые ошибки до того, как код увидит человек. Система контроля версий (Git) обеспечивает прозрачность истории изменений и позволяет безопасно откатить любые правки. Только комплексный подход гарантирует, что в основную ветку попадёт надёжный и рабочий код.
